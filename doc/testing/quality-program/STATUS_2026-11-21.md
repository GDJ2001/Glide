Raw traces are in `build/benchmarks/after-isolation-*.json`. The 5 GB UI-callback stability threshold failed in one of five runs; that result remains open. The 100 MB quarter ratios are too short to judge sustained behavior. The 5 GB backend median is above its recorded baseline (236.32 MB/s payload, 168.95 MB/s verified), while the 5 GB UI path median is above its recorded payload baseline (189.96 MB/s) and near its verified baseline (155.16 MB/s). Runs were on loopback, not the two-PC link.

## Open acceptance gates

1. Install and inspect frozen artifacts on Windows and Ubuntu 26 VM, including upgrade, restart, uninstall, and retained data. The VM was unlocked but its guest screen could not be controlled reliably through the available window automation; the WSL2 build is separate evidence.
2. Run the single aggregate Android instrumentation task successfully. The same 18 tests passed when run as five classes after a cold Pixel_10a restart; the aggregate invocation previously hit an emulator startup ANR.
3. Repeat 5 GB UI-callback stability measurements under controlled conditions and investigate the 0.79 final-quarter run. Run 10 GB, mixed-folder, 1,000-file, cancellation, startup, and 30-minute soak measurements against matched baselines.
4. Execute available Windows/Linux/Android directed installed transfers, physical two-PC cases, and hash comparisons. A loopback suite and emulator UI tests do not substitute for those transfers.
5. Complete the main Windows/Linux feature-view-model and Android runtime decomposition described in the audit plan. The current source still has large main view models and runtime/coordinator classes. Preserve behavior and add characterization tests before further splitting.
6. Check full accessibility and visual states on installed Windows and Ubuntu 26 at scaling and light/dark modes.

Do not label any open gate as passed from source inspection, package creation, or older reports.
