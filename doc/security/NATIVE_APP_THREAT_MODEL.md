# Native Glide application threat model

Updated 2026-10-13. Scope: local-network file sharing and pair-only enrollment between Android, Windows, Linux, iOS/iPadOS, and macOS. Browser file transfer is retired. The status column records current source evidence; it does not imply physical interoperability. Apple source in the completion audit awaits target-host compilation because GitHub Actions is disabled and no local Mac runner is available. The new Profile 2 Windows/Linux/Android physical gates also remain open.

| Threat / boundary | Required control | Production source | Status | Phase 2 evidence required |
|---|---|---|---|---|
| Discovery impersonation | Treat mDNS (`_glide._tcp`) and display names as availability candidates only; never advertise PINs, tokens, trust status, or certificate fingerprints in DNS-SD; bind sessions to live TLS 1.3 server certificate SPKI and cryptographic proofs | `MdnsDiscoveryService`, `LanTxtCodec`, `BonjourService`, `DesktopPairingCoordinator`, `Profile2PairingEngine`, `DesktopTransferEngine`; Android `transport-lan`; Apple `GlideTransferEngine` / `Profile2PairingEngine` | Multi-NIC IPv4 mDNS and canonical TXT source implemented; C#/Kotlin contract tests pass; current Apple source awaits macOS CI | Cross-platform wrong-PIN, wrong-endpoint, replay fixtures and physical wrong-device attempt |
| Offline PIN guessing / MITM on desktop pairing | Use pinned BoringSSL SPAKE2 (`3fed4f207543470b3d639db6ed40737e30308b51`) over TLS 1.3 (`GLD2` / `PAIR_ONLY`), 120-second one-use 6-digit code, max 3 failed attempts per window, directional HKDF key-confirmation MACs and mutual ECDSA P-256 identity signatures bound to live TLS SPKI, explicit approval on both devices, and zeroing of secret buffers | `GlideSpake2`, `Profile2PairingEngine`, `PairReadyWindowAuthority`, `DesktopPairingCoordinator`, `CGlideSpake2` | C# targeted tests pass; Apple responder/initiator source added but not yet compiled or exercised on Mac | Live Windows↔Windows, Windows↔Linux, and Linux↔Linux 6-digit pairing runs |
| Pair-only vs. transfer confusion or unapproved file delivery on `PAIR_ONLY` | Strictly separate `PAIR_ONLY` (`glide://pair/v2#...`, `purpose=pair-only`) from `glide://pair/v1#...` transfer invitations; reject any `HELLO`, `OFFER`, `DATA`, or transfer record on `PAIR_ONLY`; require explicit recipient consent for every incoming file offer, even from paired peers | `LanSessionPreambleInspector`, `DesktopProfile2Router`, `Profile2PairingEngine`, `DesktopTransferEngine`, `LanTransferTransport`, `GlideTransferEngine` | Source routes pair-only sessions away from the offer path; cross-platform live rejection remains unverified | Reject and trusted-peer interactive offer tests on all clients |
| Wrong recipient for sender-hosted QR | Confirm recipient identity before sending selected files | `DesktopTransferEngine.SendHostedAsync`, Windows/Linux recipient prompt | Linux and Windows prompts wired and tested | QR role in both directions, cancel and wrong-name cases |
| Oversized or malformed records | Bound control frames to 16 KiB and bulk chunks to 64 KiB, reject unexpected controls, unknown preambles, and unknown Profile 2 purposes | `PrefixedStream`, `LanSessionPreambleInspector`, `Profile2WireCodec`, `LanRecordChannel`, `DesktopTransferEngine`; Android protocol codec; Apple `LanRecordChannel` | .NET, Android, and Apple enforce 16 KiB control ceiling and fail closed on unknown versions/purposes | Shared malformed and boundary fixtures in Kotlin/C#/Swift |
| Quarantine bypass or corrupt file | Private staging; independently hash actual bytes; compare declared length and ITEM_END digest; commit only after verification | .NET `QuarantineStagingStore`/`DesktopTransferEngine`/`DesktopBatchPreparer`; Android `QuarantineStagingStore`; Apple `QuarantineStagingStore` | Desktop, Android, and Apple stage into `.part` quarantine files, verify streaming SHA-256 against `ITEM_END`, and atomically rename only on match | Corrupt digest, truncation, symlink, collision, disk-full, and restart cases |
| Unwritable receive destination | Check the selected destination before asking for offer consent; never claim receipt when verified bytes cannot be committed | .NET `QuarantineStagingStore.VerifyDestinationWritableAsync`, `DesktopTransferEngine`; Windows/Linux Settings destination pickers | Desktop rejects an unwritable destination with a typed storage result before consent; unit test passed on Windows and Linux-local test host | Installed Ubuntu 26 receive to writable and read-only destinations, Windows-to-Linux retry, and destination-change cases |
| Cancellation misreported as pairing or trust failure | Propagate coroutine cancellation and keep service shutdown distinct from an operation error | Android `TransferRuntime` | Pairing and trust catches now rethrow `CancellationException`; lifecycle regression and Android unit tests passed | Physical cancel and service-restart UI check on Android |
| Persistent identity misuse or silent key substitution on trusted reconnect | Enroll peer public key only after mutual cryptographic proof (`PAIR_CONFIRM`) and both users' explicit approval; on `TRUSTED_SEND`, require mutual `identity-v1` signatures over `GLIDE-TRUSTED-SESSION-V1` bound to current TLS certificate SPKI before any file offer; allow TLS certificate renewal only when persistent identity proof matches; fail closed with `Identity changed — pair again` on key change or revocation | `DesktopPersistentTrustManager`, `DesktopTrustedSessionAuthenticator`, `DesktopTransferEngine.SendTrustedAsync` / `ReceiveTrustedAsync`; Android `PersistentTrustManager` / `LanTransferTransport`; Apple `PersistentTrustStore` / `GlideTransferEngine` | Source path implemented; desktop targeted tests pass; no current cross-platform physical trusted-send evidence | Enrollment, cert rotation, identity rotation, and revocation tests |
| Concurrent process or batch conflict | One active batch or pairing operation and one per-user listener owner; return `This device is busy — try again` (`BUSY`) on concurrent pairing/transfer attempts | `DesktopTransferRuntime`, `DesktopPairingCoordinator`, `DesktopListenerSupervisor`, `DesktopListenerOwnership`, `TlsSocketListener`, `LinuxSingleInstance` | Single active session ownership enforced across pairing and transfer engines | Duplicate launch, stalled handshake, and concurrent pairing/transfer cases |
| Secret leakage | Never transmit or log 6-digit PINs, raw invitation tokens, full URIs, or private keys; zero PAKE secret buffers after use; restrict desktop and mobile trust/identity stores | `LanInvitation.ToString`, `LanPairV2Invitation.ToString`, `PairReadyWindowAuthority`, `GlideSpake2`, `DaemonInvitationFile`, platform trust stores | Redacted `ToString()`, zeroed PAKE/PIN buffers, and restricted store permissions verified | Log/notification scan and store permission checks |
| Stale or substituted artifact | Build every package from one clean commit; record toolchain and fresh hash; sign outside untrusted PR jobs | `tools/package-*`, `apple/scripts/package-*`, CI workflows | Version preserved at `1.0.0` across all packages | Manifest hash/provenance, install/upgrade/uninstall on target OS |

Residual blockers: the current Apple target-host build, physical iPhone/iPad and Mac execution, and the new Profile 2 Windows/Linux/Android pairing and trusted-send interoperability matrix. Older Profile 1 transfer evidence does not clear these gates.
