## Objective and evidence rule

Carry the now user-reported satisfactory Windows LAN behavior to Linux, Android, macOS, and iOS while preserving security and reliable completion. Do not set a universal MB/s target for Wi-Fi or phones. For each device pair, first measure the independently usable link and storage rate with a comparable transfer. Judge Glide against that same pair, direction, source, destination, and conditions. Report payload-only throughput separately from acceptance-to-verified-completion throughput. A throughput result is invalid without matching independent source/destination SHA-256 and a truthful terminal UI result.

Every result must identify commit, artifact SHA-256, device/OS, Wi-Fi or Ethernet PHY, negotiated rate, storage locations, file size, transfer direction, build mode, power/thermal state, and whether it is automated, VM/simulator, or physical. The Windows fix is user-reported as successful; the older [Windows status record](../testing/evidence/WINDOWS_1GBPS_TRANSFER_STATUS.md) contains loopback evidence and an unclosed formal two-PC measurement gate. Do not silently convert the user report into that gate's trace evidence.

## Stage 1 — shared Linux desktop runtime

1. Verify the Linux GUI and CLI instantiate `DesktopTransferEngine` with `DesktopTransferIoOptions.Default`, not `LegacyBaseline`. Confirm `LanRecordChannel` uses the optimized ordered writer and the UI progress callback does not block streaming. Add an integration test that covers the installed Linux entry path rather than only the engine in isolation.
2. Measure Linux→Windows, Windows→Linux, and Linux→Linux, including a VM/WSL measurement labeled as virtual and an independent physical Linux host measurement labeled physical. Segment payload, verification, and commit. A fast network phase followed by a slow full-file copy is a storage problem, not a link problem.
3. If commit is the measured bottleneck, implement an **opt-in Linux same-filesystem staging policy** only after checking mount/device identity, private owner-only directory permissions, symlink/path replacement, available space, and no overwrite. Use descriptor-relative/no-follow operations and `renameat2` or an equivalent safe no-replace publication where supported. Independently reread and SHA-256 verify before publication, preserve the verified file identity through rename, and fall back to the existing verified-copy path whenever proof fails. Avoid relying only on path strings or `DriveInfo` mount-prefix comparison as a security proof.
4. Test ext4 plus the actual user's destination type; test a separate mount, bind mount, symlink/reparse attempt, collision, disk full, cancellation, crash/restart cleanup, and a destination changed between preflight and commit. Never delete active staging. Keep verified history and trust records through upgrade.

## Stage 2 — Android LAN transport and storage

1. Benchmark a release-like installed APK on a physical Android device in both send and receive directions to Windows and Linux. Capture Wi-Fi negotiated rate, RSSI, phone thermal throttling, source `ContentResolver` time, TLS rate, pipe occupancy/wait, private staging write, digest verification, MediaStore/SAF publication, and UI/notification callback cost. Record provider kind and whether its bytes are local or cloud-backed.
2. Preserve one serialized TLS writer and one reader. The current source change batches ordered Profile 1 DATA frame bytes in a bounded 256 KiB buffer, flushes at data thresholds and every control/stream-end boundary, and removes a DATA payload copy on receive. Verify fragmented/coalesced records, partial reads, one-byte reads, control latency, cancellation, errors, and interoperability with the previous Android, Windows, and Linux builds. Avoid a task or allocation per chunk and never let a buffered tail wait indefinitely for a peer response.
3. If traces show `PipedInputStream`/`PipedOutputStream` or per-chunk progress as the bottleneck, replace only that measured segment with a bounded owner-aware queue or throttle progress to the existing UI budget. A full queue must apply backpressure; no dropped bytes, unbounded coroutines, or main-thread file I/O. Keep source/staging hashing and independently verified destination bytes. Do not change `:transfer-core`'s zero-Android dependency boundary.
4. Keep verified files automatically saved to the configured Android destination, default `Download/Glide`, as previously chosen. Treat MediaStore/provider finalization as a separate visible Saving phase. Test storage permission loss, unavailable provider, filename collision, low space, app background/foreground, process death, and cancellation. Preserve paired identities, settings, and verified history.

## Stage 3 — macOS and iOS common Swift engine

1. Use a **Mac host** for `swift test` and Xcode builds of `GlideMac`, `GlideIOS`, and the Share Extension. Do not enable GitHub Actions. Without that host, source review and Windows-side checks are all that can be reported.
2. Add monotonic phase diagnostics to `GlideTransferEngine` and `QuarantineStagingStore`; sample hot-path metrics without per-record console logging. Measure `NWConnection.send` completion cost and `readExact` allocations before choosing batching. Any batching must preserve ordered control delivery, a prompt flush at item/control boundaries, bounded memory, one in-flight writer owner, cancellation, and exact Profile 1 bytes. Prove old/new interoperability through shared fixtures.
3. Profile the current second full-file copy in Apple commit. A fast same-volume path requires private staging on the target APFS volume, no-follow/owner checks, independent stored-byte SHA-256, handle/file-ID binding from verification to atomic no-replace publication, collision handling, and a verified-copy fallback. File-provider/iCloud destinations may require the fallback. Never make an unverified file visible to the user.
4. macOS and iOS share core transfer tests but need separate installed behavior checks: macOS native app receive/send, iOS foreground/network lifecycle, Files picker/provider, Share Extension handoff, background interruption, low-storage warning, and physical phone↔desktop transfers. Simulator and unsigned archive results do not substitute for signed iPhone evidence.

## Shared correctness, performance, and delivery gates

- Correctness: old↔new client interoperability both directions; QR, link, paired reconnect; consent, rejection, cancellation, network loss; malformed lengths; order, duplicate and zero-byte files; digest mismatch; 4 GiB and 4.5–5 GB boundaries; disk full; restart cleanup; all success paths independently SHA-256 match. A receiver-committed file with lost final ACK must be reported as uncertain, not silently declared lost.
- Performance: measure at least five repeat runs per principal large-file direction. Report median, worst run, one-second and five-second payload windows, first steady quarter versus final quarter, acceptance-to-verified duration, CPU, memory/PSS, allocations/GC, disk latency, retransmits, and failure count. The target is at least 95% of the **measured usable capacity for that exact pair** where storage supports it; at least 95% of five-second payload windows should exceed 85% of that pair's baseline, and the final quarter should average at least 90% of the first steady quarter. If provider/thermal limits make this impossible, document the measured constraint instead of tuning by guesswork. Do not hide a commit or verification pause inside a smooth network speed number.
- Stability: bounded buffers with no growth proportional to file size; 30-minute repeated-transfer run; responsive cancellation and complete handle/temporary-file cleanup; one terminal result per attempt. Report any stalled provider or OS I/O explicitly.
- Checks: `pwsh -NoProfile -File tools/check-architecture.ps1 -FailFast`; `dotnet test desktop/Glide.slnx -c Release --verbosity quiet`; from `android/`, `.\gradlew.bat :android:transport-lan:testDebugUnitTest :android:app:testDebugUnitTest :android:app:lintDebug :android:app:assembleDebug --no-daemon --console=plain`; on Mac, `apple/scripts/build-and-test.sh` plus target builds as documented in `apple/scripts/run-backend-tests.sh`. Run targeted tests immediately after each source edit, then full gates after implementation.
- Installed evidence: produce fresh packages for affected platforms from one final commit, record compiler/toolchain and SHA-256 manifests, install on target hosts, preserve previous compatible packages for rollback, and prove retained settings/trust/history. Attach both-side transfer results and hashes. Report implemented, built, installed, automated-tested, VM/simulator-tested, and physically verified as distinct states. Missing Mac host, signing, physical Linux host, or phone means that gate is **blocked**, never passed.

## Execution order and stop rules

Complete the source/fixture safety gate first, then Linux shared-path measurement, Android physical measurement, Mac common-engine measurement, and platform-specific storage changes only where traces justify them. Make bounded commits by stage, each with a measured before/after and an exact failure rollback. Finish with cross-platform interoperability and installed artifact gates. Do not merge or announce full completion while a mandatory physical gate is missing. Keep development version 1.0.0 unless a release decision explicitly changes it.
