# HARD-016 — Linux CLI/daemon lifecycle hardening

## Status

**IN_PROGRESS** on `hardening/continue-2026-09-18`.

The missing peer-specific headless authorization requirement cannot be truthfully closed until persistent cryptographic peer identities from HARD-020/HARD-021 are available.

## Implemented now

- CLI send accepts only `--pair <invitation>`; direct unauthenticated host/port sending fails closed.
- Interactive `receive` publishes one-use invitations, rotates before expiry, and explicitly asks the operator to accept an authenticated offer.
- Daemon startup fails closed unless `--accept-paired-offers` is explicitly configured.
- Headless policy accepts a configured destination and maximum offer byte ceiling.
- Daemon invitations rotate before expiry.
- Ctrl+C and Linux/macOS SIGTERM feed the same cancellation source; accept waits use linked bounded cancellation.
- Missing/no-active invitation bootstrap is rejected by the shared invitation authority.

## Remaining acceptance gap

The current one-use invitation authenticates the receiver to the sender, but does not provide a persistent cryptographic sender identity to the receiver. A daemon size/destination policy is therefore explicit and bounded, but not yet **peer-specific**. HARD-020/HARD-021 must enroll and authenticate the sending peer and bind headless authorization to that peer.
