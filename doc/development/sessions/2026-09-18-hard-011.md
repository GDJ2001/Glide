# HARD-011 — Shared desktop transfer engine extraction

**Date:** 2026-09-18  
**Status:** REVIEW_REQUIRED  
**Continuation baseline:** `17a8b021977298475e7ea75088108d66a4916311`  
**Implementation head:** `59c02f1cfd5b91a91e304af09a6530d7c1ba6c13`

## Objective

Extract one desktop application/session engine so the CLI and WPF entrypoints no longer maintain independent pairing, consent, protocol, streaming, completion, and cancellation loops.

This task intentionally centralizes the current behavior before the protocol/security/storage repairs owned by HARD-012 through HARD-016.

## Resulting responsibility map

### `Glide.Desktop`

Owns the connected desktop transfer lifecycle:

- TLS client connection for outbound sessions;
- QR bootstrap processing and one-use invitation callbacks;
- direct/unpaired SAS presentation through an interaction port;
- HELLO / HELLO_ACK;
- offer begin/page/end and offer decision;
- item start/ready/data/stream-end/item-end/item-result;
- batch end/result;
- sender and receiver file-stream loops;
- receive-side streaming SHA-256 verification;
- current sender pre-transfer hashing behavior;
- cancellation-to-result mapping;
- terminal transfer result construction;
- progress, item status and history callbacks.

Files:

- `windows/Glide.Desktop/DesktopTransferEngine.cs`
- `windows/Glide.Desktop/DesktopTransferModels.cs`

### `Glide.App` CLI

Owns only CLI/application concerns:

- argument parsing;
- one-shot listener / daemon listener creation;
- pairing invitation and terminal QR presentation;
- console interaction callbacks/log formatting;
- daemon signal/shutdown loop;
- web command routing.

`RunSendAsync`, `RunReceiveAsync`, daemon receive, and the retained HARD-003 reflection seam all delegate to `DesktopTransferEngine`.

No production `LanRecordChannel`, `MessageTypes.ItemStart`, or whole-file hashing loop remains in `Program.cs`.

### `Glide.Windows.UI`

Owns WPF concerns:

- selected file collection and controls;
- listener/mDNS lifecycle;
- pairing modal/invitation presentation;
- SAS modal user interaction;
- UI state/progress/history projection;
- transfer cancellation token;
- web-share UI.

`MainViewModel` implements `IDesktopTransferInteraction` and delegates connected send/receive work to `DesktopTransferEngine`.

No production `LanRecordChannel`, protocol item loop, or whole-file hashing loop remains in `MainViewModel.cs`.

### Existing lower layers

- `Glide.Core`: protocol models/codecs, identifiers, pairing codec, SAS helper, staging/path primitives.
- `Glide.Transport`: TLS sockets, LAN record channel/framing, discovery, web transport.
- `Glide.Desktop`: orchestration/application session layer.
- CLI/WPF: presentation and host lifecycle.

## Behavioral tests added

### `DesktopTransferEngineTests`

Uses real loopback TLS and the actual shared engine:

1. QR-paired two-file sender + receiver journey through the same engine.
2. Sender and receiver both observe canonical peer identity and invitation consumption.
3. Both sides emit verified item/history evidence.
4. Destination payload bytes match source payload bytes.
5. Receiver offer rejection stops before file commit and yields rejected results on both sides.
6. Pre-cancelled sender returns a cancelled result rather than entering the protocol session.

### `DesktopEngineArchitectureTests`

Guards the extraction boundary:

- CLI and WPF must reference `DesktopTransferEngine`;
- neither entrypoint may construct `LanRecordChannel`;
- neither entrypoint may contain `MessageTypes.ItemStart`;
- neither entrypoint may contain production `File.ReadAllBytesAsync`;
- solution/CLI/WPF project files must reference `Glide.Desktop`.

## HARD-003 compatibility

The red-before-fix desktop regressions remain meaningful:

- the private CLI `HandleConnectionTransferAsync` method was retained as a thin engine wrapper because HARD-003 invokes it through reflection;
- non-daemon SAS console output retains the original six-digit-code format so the direct-SAS regression still compares the two independently generated codes;
- the shared engine intentionally retains current one-page pagination, sequence behavior, direct-SAS nonce behavior, and whole-file pre-transfer hashing.

Therefore HARD-003 defects continue to map to their intended later tasks rather than failing because the extraction removed the test seam.
