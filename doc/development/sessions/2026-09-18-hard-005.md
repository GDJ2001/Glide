## Result

HARD-005 replaces production ownership of active Android transfer/pairing execution with one process-singleton `TransferRuntime` whose active coordinator and pairing jobs execute only after the foreground service attaches its service scope.

Production `TransferViewModel`, Navigation3 composition, `MainActivity`, `GlideApplication`, and `TransferService` no longer use `TransferSessionManager` or `ActiveSessionTracker` as their active-session authority.

## Runtime boundary delivered

`TransferRuntime` now provides:

- immutable transfer, pairing, discovery placeholder, active-session and active-session-ID state;
- typed commands for sender/receiver startup, pairing bind/confirm/reject, offer accept/reject, exact-session cancel, process-lifetime resume, and receive-availability intent;
- service-scope attachment/detachment with rejection of active ownership migration;
- idempotent same-session startup and rejection of a competing active session;
- exact-session validation for runtime actions;
- terminal snapshot/retry metadata preservation;
- service-detach interruption semantics so active work cannot silently continue in a ViewModel/application scope.

The receive/discovery command surface remains deliberately fail-closed until HARD-006 supplies the real production discovery and permission dependencies.

## Presentation/service changes

- `TransferViewModel` observes `TransferRuntime` and forwards typed commands. Its `viewModelScope` remains only for UI-local export work.
- Navigation3 constructs the transfer ViewModel around the injected process runtime, so Activity/ViewModel recreation observes the same owner.
- `TransferService` attaches/detaches the runtime service scope and routes notification actions through exact-session runtime commands.
- `MainActivity` debug fixtures and ingress busy-state checks use runtime state.
- `GlideApplication` exposes runtime active-session identity to orphan-maintenance logic.

Legacy singleton files are retained for historical/test compatibility where still referenced, but they are no longer the production authority on these paths.

## Behavioral evidence

Dedicated `TransferRuntimeTest` coverage proves:

1. coordinator/pairing work fails closed before a service owner exists;
2. same-session duplicate startup is idempotent;
3. a competing active session is rejected;
4. stale cancel IDs are rejected while the exact active ID succeeds;
5. two ViewModels recreated over the same runtime observe one coordinator owner;
6. pairing observation/confirmation is runtime-owned and duplicate confirmation is rejected;
7. detaching the service interrupts non-terminal ownership and preserves recoverable state;
8. receive availability remains fail-closed until HARD-006.

Existing pairing, lifecycle, permission, stale-notification and transfer ViewModel tests were migrated to the runtime boundary where applicable.
