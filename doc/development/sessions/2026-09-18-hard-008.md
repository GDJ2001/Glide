## Implemented production path

HARD-008 removes the fixed/example Android receive-QR path and routes LAN QR pairing through service-owned production transport state.

### Receiver

- Added `ProductionLanController` as the service-scoped owner of:
  - `LanNetworkScope`
  - a fresh `LanLeaseIdentity` (Android Keystore in production)
  - a live `LanListener` bound to an ephemeral port
  - the exact `InvitationAuthority` used by the listener bootstrap
  - `LanTransferTransport`
- QR invitations are minted only after an eligible local network and live listener exist.
- Invitation endpoints use current on-link addresses plus the listener's actual bound port.
- The SPKI pin is derived from the current lease identity; production no longer supplies an example pin.
- The invitation authority is attached to the same receiver transport, so BOOTSTRAP consumption is atomic.
- Listener/invitation resources are revoked on dismiss, refresh, expiry, route replacement and service teardown.
- After authenticated bootstrap, the listener closes while the connected transport remains owned by the foreground service and enters the ordinary receiver coordinator.

### Sender

- `GlideRoute.QrScanner` now carries the prepared batch ID.
- Camera scan and paste still share one strict invitation decoder/confirmation flow.
- Explicit confirmation plus required local-network permission starts `TransferService` with the exact invitation and prepared batch ID.
- `TransferRuntime` registers the invitation with `LanTransferTransport`, performs pinned TLS + bootstrap, and starts the ordinary sender coordinator only after authenticated connection.
- Switching to LAN clears outstanding Nearby pairing/discovery state to prevent cross-transport races.
- QR connection events no longer replay, preventing a recreated scanner collector from re-firing an old `ConnectConfirmed` action.

## Production placeholder removal

Direct current-file inspection of `GlideAppNavDisplay.kt` confirmed:

- historical endpoint `192.168.1.50:4242` is absent from the production navigation source;
- historical fixed 64-hex example SPKI is absent;
- receive QR state comes from `TransferRuntime.lanReceiverState`;
- sender QR route preserves the selected batch ID.

Example IPs and pins remain in unit-test fixtures and documentation examples where they are intentionally non-production data.

## Added behavioral tests

### `Hard008LanQrProductionFlowTest`

Uses the actual LAN TLS listener/connector/bootstrap implementation over an IPv4 loopback harness and covers:

1. live listener -> invitation with actual bound port and generated lease SPKI;
2. successful pinned TLS/bootstrap connection between production LAN controllers;
3. wrong SPKI pin fails before authenticated receiver connection;
4. listener bind failure surfaces a retryable error and mints no invitation;
5. invitation consumes exactly once;
6. replay is rejected with `INVITATION_USED`;
7. expiry is rejected with `INVITATION_EXPIRED`.

### `Hard008LanRuntimeHandoffTest`

Covers:

1. prepared two-file batch + scanned invitation -> authenticated LAN bootstrap -> service-owned sender coordinator with full source map;
2. service-owned live receiver QR -> authenticated LAN bootstrap -> service-owned receiver coordinator.

### Existing QR tests updated

`QrPairingViewModelTest` and `UnifiedQuickShareTest` now subscribe to the non-replaying connection event before confirmation.
