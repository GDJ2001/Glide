## Implemented profile corrections

### DNS-SD

Windows now uses the same invitation-discovery contract as Android:

- service: `_glide._tcp.local.`
- `v=1`
- `tv=1`
- `q=1`
- `p=<32 lowercase hex presence id>`
- `dn=<bounded device name>`
- `dt=phone|tablet|desktop|unknown`

The desktop encoder no longer advertises certificate fingerprints, pairing tokens, filenames, legacy `alpn=glide-v1`, or unimplemented capability bits. The decoder requires the profile/version/pairing fields, validates presence/name/device-type bounds, ignores only bounded unknown keys, and uses the SRV port instead of a fixed discovery port.

### TLS

- TLS 1.3 remains mandatory.
- ALPN is now exactly `glide-lan/1`; the legacy `glide-v1` fallback was removed.
- Desktop receiver TLS no longer requires a client certificate for initial QR pairing, matching Android's server-authenticated pinned-TLS design.
- Desktop sender continues exact SHA-256 SPKI pin validation from the QR invitation before application records are sent.
- Explicit post-handshake ALPN checks fail closed.

### Bootstrap authority

The old direct/unpaired SAS production path is disabled. LAN sending requires a decoded QR/pairing invitation.

A new thread-safe `LanInvitationAuthority` owns the desktop receive invitation and:

- stores a hash of the bearer token rather than using it as mutable authorization state;
- compares the token hash and invitation hash in constant time;
- applies a monotonic expiry boundary after construction;
- atomically consumes exactly once under a lock;
- rejects replay with `INVITATION_USED`;
- supports explicit revocation when WPF listening stops.

CLI and WPF receivers now share one authority instance across accepted sockets instead of re-creating authorization per connection. The CLI daemon no longer enables invitation-less bootstrap; peer-specific unattended receiving remains for HARD-016.

### Product entry points

- CLI receive binds an ephemeral listener port by default; `--port` is explicit.
- CLI sending requires `send --pair <invitation> <files...>`; raw host/port send is disabled.
- WPF discovery is treated as an endpoint hint only. Sending requires a live pairing invitation.
- WPF listener advertisement uses the actual listener port and the invitation's random presence id.
- Current Windows documentation was corrected to describe this profile and to stop treating historical test counts as current-head evidence.

### Cross-language helper cleanup

The older `transfer-core` LAN discovery helper now uses `glide-lan/1` and emits the same `v/tv/q/p/dn/dt` record, preventing tests or future code from reviving the stale `glide-v1` / fingerprint / capability advertisement.

## Tests prepared

New/updated tests cover:

- exact desktop DNS-SD encoding compatible with Android;
- rejection of the stale discovery profile and malformed presence/device type;
- TLS 1.3 certificate-less QR client acceptance by the desktop receiver;
- rejection of legacy `glide-v1` ALPN;
- concurrent invitation redemption with exactly one accepted consumer;
- wrong-token attempts not consuming the valid invitation;
- production direct/unpaired send failing closed;
- HARD-003 pagination, sequence and bounded-hashing regressions continuing through an authenticated QR bootstrap instead of failing early at the new pairing gate;
- existing shared-engine send/receive tests using the one-use authority.
