# HARD-018 — Identity/resume protocol hardening preparation

## Status

**REVIEW_REQUIRED / pre-gate implementation** on `hardening/continue-2026-09-18`.

HARD-017, the native cross-platform interoperability gate, is still BLOCKED. HARD-018 source preparation was performed to remove unsafe/stale protocol assumptions and establish the cross-language contract, but this record does not claim the M3 gate is open or that trusted sessions/resume are production-enabled.

## Problem found

The pre-hardening identity/resume extension was not sufficient for production trust:

- `IDENTITY_RESPONSE` effectively signed only a random nonce.
- Resume proof fields were underspecified and not canonically serialized across Kotlin/.NET.
- Neither proof bound both peer identities, roles, active session, negotiated capabilities, and the actual secure channel.
- `identity-v1` and `resume-v1` were advertised as default optional Android capabilities even though runtime trust/channel-binding integration was incomplete.
- A known peer presenting a different fingerprint could fall back to first-use pairing in the JVM helper.

These behaviors contradicted the active hardening plan.

## Implemented protocol contract

### Canonical transcripts

Added matching implementations:

- `transfer-core/src/main/kotlin/dev/glide/core/protocol/IdentityResumeTranscript.kt`
- `windows/Glide.Core/Security/IdentityResumeTranscript.cs`

The signed value is binary, not JSON:

- domain `GLIDE-SIGN-V1\0`;
- purpose byte (identity/resume);
- length-prefixed UTF-8 strings;
- big-endian numeric fields;
- canonical lowercase hashes/fingerprints.

Capability hashing uses `GLIDE-CAPS-V1\0` with sorted distinct capability strings.

### Shared golden vectors

Added:

`protocol/fixtures/identity_resume_v1_vectors.json`

Fixture hashes:

- capability set SHA-256: `992a66ad3dccb3c5190e046f92b6190751644f1f98946ac6511350952d333b47`
- identity transcript SHA-256: `24a83cd012dc70ef8738ac66dcab7e4b16232b8ab74ea07e7ed6480416abb3a4`
- resume transcript SHA-256: `429764ab0fc8bfcd25a89b4018d889bb8c656afdc50e6b292aa4c0633e5dcb21`

Kotlin and .NET tests load the same fixture and compare byte-for-byte transcript output.

### Message schema

`IDENTITY_CHALLENGE`, `IDENTITY_RESPONSE`, `RESUME_REQUEST`, `RESUME_ACCEPT`, and `RESUME_REJECT` now have explicit profile/version fields and correlation/binding data.

Resume rejection uses a stable code catalog instead of free-form remote authority.

### Strict validation

Both Kotlin and .NET codecs reject:

- unsupported extension profile;
- noncanonical/uppercase fingerprint/hash fields;
- invalid roles and resume direction;
- malformed key/signature hex;
- invalid UUID correlation fields;
- invalid chunk sizes;
- offsets beyond source size;
- non-chunk-aligned progress;
- mismatched verified chunk count;
- unknown resume rejection codes.

### Capability gating

`stream-v1` and `sha256` remain required.

`folder-v1` is the current production optional capability.

`identity-v1` and `resume-v1` are defined as trust-extension capabilities but are **not advertised by default** until HARD-019–021 provide persistent key storage, enrollment, channel binding, and trusted-session enforcement.

`resume-v1` requires `identity-v1`.

### Signature API hardening

The JVM/Android identity abstraction no longer exposes a nonce-only signing API.

- `signNonce` → `signTranscript`
- `verifyNonceSignature` → `verifyTranscriptSignature`

The Android Keystore adapter signs caller-supplied canonical transcript bytes.

### Known-peer mismatch

`PeerIdentityVerifier.verifyPeerTrust` now fails closed when a known peer presents either a different fingerprint or a different public key. It no longer treats a changed known key as ordinary first-use pairing.

## M2 interoperability correction discovered during HARD-018

Desktop HELLO/HELLO_ACK capability negotiation was also inconsistent with the Android protocol:

- desktop HELLO had an empty required-capability set;
- desktop HELLO_ACK advertised `lan-v1`.

The shared desktop engine now requires/acknowledges the canonical `stream-v1` + `sha256` capabilities with `folder-v1` optional, and rejects unsupported/unoffered ACK capabilities.

This correction is part of HARD-012/HARD-017 interoperability evidence, not proof that HARD-017 passed.
