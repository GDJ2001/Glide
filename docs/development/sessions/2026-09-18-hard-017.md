## Evidence tooling prepared

### Deterministic multi-page corpus

`tools/new-hard017-corpus.ps1` generates a deterministic native-transfer corpus with:

- 35 items;
- 32 small deterministic binary files;
- one zero-byte file;
- one 10 MiB file;
- one >=100 MiB file;
- per-item SHA-256;
- corpus total bytes;
- explicit offer page count using the 32-item desktop page boundary.

The default corpus therefore forces at least two offer pages and simultaneously covers empty, small, mixed and large payloads.

Generated payloads live under `build/` or the chosen external evidence directory and are not committed as fake evidence.

### Exact endpoint/build identity

`tools/capture-hard017-endpoint.ps1` captures the exact endpoint used for a physical run.

For every platform it records:

- repository HEAD;
- artifact path/name/size;
- artifact SHA-256;
- runtime framework.

Android additionally records:

- physical device serial;
- manufacturer/model;
- Android release/API;
- security patch;
- build fingerprint;
- installed package/version information.

The Android capture rejects emulator/qemu/goldfish/ranchu-style devices.

Windows/Linux captures record real OS/runtime/machine architecture identity and the exact binary hash.

All three endpoint records must resolve to the same repository HEAD.

### Fail-closed evidence verifier

`tools/verify-hard017-evidence.ps1` refuses certification unless the evidence directory contains all required identities, hashes, logs and outcomes.

Required success directions:

1. Android → Windows
2. Windows → Android
3. Android → Linux
4. Linux → Android
5. Windows → Linux
6. Linux → Windows

Each success must use the multi-page corpus, retain sender/receiver logs, report successful terminal batch status and prove byte-identical per-item hashes.

For each unordered platform pair — Android/Windows, Android/Linux and Windows/Linux — the verifier also requires:

- explicit offer rejection;
- mid-transfer cancellation;
- wrong-authentication rejection;
- fresh-invitation reconnect after a prior non-successful session.

That produces 12 negative/recovery cases in addition to the six success directions.

The verifier fails if:

- any direction/case is absent;
- endpoint repository heads differ;
- artifact hashes do not match the captured endpoints;
- the corpus does not exceed 32 items;
- zero-byte or >=100 MiB coverage is absent;
- sender/receiver logs are missing or empty;
- a reject/cancel/authentication failure reports successful batch status;
- wrong authentication authorizes payload bytes;
- reconnect reuses stale authority or lacks final byte-identical hash proof.

A passing structural audit still requires human log review for authenticity and protocol behavior.

## Important distinction: Android device smoke test

The existing:

`app/src/androidTest/kotlin/dev/glide/app/transfer/LanDeviceTransferSmokeTest.kt`
