## Implemented session-state repairs

### Independent monotonic direction sequencing

`DesktopSessionProtocol` now owns one outgoing and one incoming sequence counter for the authenticated session.

- Each direction begins at `seq=1`.
- Every emitted control increments exactly once.
- Every inbound control must match the next exact sequence.
- Gaps/replays fail with `PROTOCOL_ORDER`.
- Peer `messageId` values must be unique within the live state.
- Every inbound envelope must carry the exact authenticated `sessionId`.

The former fixed sender values (`5`/ `6` reused for every item) and fixed receiver values (`4`/`5`/`6`) are removed.

### Exact state/type/correlation checks

Every blocking control transition now specifies the only legal next message type and, where applicable, exact `batchId` and `itemId`.

The sender validates:

- `HELLO_ACK`;
- `OFFER_DECISION` for its exact batch;
- `ITEM_READY` for the exact current batch/item;
- `ITEM_RESULT` for the exact current batch/item;
- `BATCH_RESULT` for the exact batch.

The receiver validates:

- `HELLO` for the bootstrap session;
- `OFFER_BEGIN`;
- each exact contiguous `OFFER_PAGE`;
- `OFFER_END` for the same batch;
- each `ITEM_START` for the accepted item in preserved order;
- `ITEM_END` for that same item;
- `BATCH_END` for the accepted batch.

### Protocol negotiation

Desktop HELLO/HELLO_ACK now use the V1 required capabilities `stream-v1` and `sha256`.

- Sender HELLO offers protocol major 1 and those required capabilities.
- Receiver rejects a HELLO that does not offer major 1 or required capabilities.
- Sender rejects a HELLO_ACK that does not return the required capabilities.
- Sender also obeys the receiver's negotiated max-item/max-batch/max-control limits before offering data.

### Real offer pagination and assembly

Sender offer generation now:

- preserves item order;
- caps each page at 32 items;
- paginates earlier when the encoded control would exceed the peer's negotiated control limit;
- caps accumulated offer metadata at 1 MiB;
- advertises the real `pageCount`.

Receiver offer assembly now:

- requires contiguous zero-based page indexes;
- requires all page batch IDs to match;
- rejects duplicate item IDs;
- checks accumulated metadata size;
- checks assembled item count and byte sum against `OFFER_BEGIN`;
- waits for a matching `OFFER_END`;
- only then calls the user consent interaction.

Malformed/incomplete metadata therefore cannot reach the consent UI.

### Stream/item correlation

For every accepted item:

- `ITEM_START` size must equal the accepted offer;
- `bulkRef` must be unique in the session;
- DATA and STREAM_END must use that exact `bulkRef`;
- receiver rejects bytes beyond the offered size;
- STREAM_END byte count must equal the bytes actually read and the accepted size;
- `ITEM_END` must correlate to the exact batch/item;
- sender only marks an item verified if the returned receipt size and SHA-256 exactly match what it sent.

### Truthful item and batch outcomes

A failed `ITEM_RESULT` now terminates the sender's unfinished batch instead of continuing.

On receiver integrity failure:

- quarantine is purged;
- one failed `ITEM_RESULT` is sent;
- the remaining batch terminates;
- no `BATCH_RESULT completed` is emitted.

`BATCH_END` is emitted/accepted only after all accepted items are verified. A completed `BATCH_RESULT` must exactly match the accepted offer's verified item count and byte total.

### Deadlines

The shared session guard applies cancellable protocol deadlines for:

- bootstrap/result: 30 s;
- HELLO/ACK: 10 s;
- offer-page gaps: 10 s;
- offer consent/decision: 120 s;
- ITEM_READY: 30 s;
- first bulk record: 30 s;
- later bulk progress: 60 s;
- post-stream item receipt: 120 s;
- terminal BATCH_RESULT: 10 s.

`DesktopProtocolDeadlines` is injectable so tests can prove timeout behavior without sleeping for production intervals.

Cancellation is observed before QR/session validation so an already-cancelled operation stays terminal without starting authentication.
