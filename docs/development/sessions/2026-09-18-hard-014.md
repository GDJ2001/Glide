## Sender hashing repair

The production desktop sender no longer calls `File.ReadAllBytesAsync` or computes a whole-file digest before the offer.

For each selected source it now:

1. captures the offered file length once;
2. sends metadata using that captured length;
3. opens the source only after `ITEM_READY`;
4. reads at most one bounded LAN chunk at a time;
5. writes that chunk to the LAN channel;
6. appends exactly the successfully written bytes to shared `StreamingSha256`;
7. rejects source length growth/shrinkage relative to the accepted offer;
8. emits `STREAM_END` and `ITEM_END` using the actual streamed byte count and same-pass digest;
9. accepts `ITEM_RESULT verified` only when the returned size/digest exactly match the bytes it sent.

The digest therefore describes the transmitted stream instead of an earlier snapshot, and managed memory is independent of file size.

## Shared streaming hash primitive

`windows/Glide.Core/Security/StreamingSha256.cs` provides the shared incremental SHA-256 accumulator used by sender and quarantine storage.

Properties:

- no full-payload buffering;
- `Int64` byte counter;
- canonical lowercase SHA-256 result;
- zero-length payload support;
- completion is single-use;
- payload memory is bounded by caller chunk size.

## Reservation-backed quarantine storage

`QuarantineStagingStore` is now the native desktop storage authority rather than only a helper.

### Reservations

`ReserveIncoming`:

- validates the declared size against protocol limits;
- validates/sanitizes the relative destination path;
- rejects reparse/symbolic-link traversal in existing destination/staging ancestors;
- tracks cumulative outstanding bytes across reservations;
- fails with `INSUFFICIENT_STORAGE` before transfer authorization when the configured staging budget cannot cover the item;
- creates no destination file and opens no payload handle yet.

The desktop receiver reserves the complete user-accepted batch **before** sending `OFFER_DECISION accepted`. If reservation fails, it sends the protocol-valid `INSUFFICIENT_STORAGE` or `DESTINATION_UNAVAILABLE` rejection and cleans any partial reservation state.

### Bounded quarantine writer

`QuarantineWriteSession` owns:

- one quarantine `FileStream`;
- one shared `StreamingSha256`;
- exact `Int64` byte accounting;
- declared-size overrun rejection before extra bytes are written;
- async bounded writes;
- digest verification;
- durable flush before publication;
- cleanup/release on cancellation, failure or disposal.

`ITEM_READY` is sent only after the reservation exists and the quarantine writer is actually open.

### Centralized commit and cleanup

The desktop engine no longer:

- constructs quarantine paths;
- creates destination directories;
- hashes receive bytes directly;
- calls `ResolveCollision`;
- calls `File.Move`;
- purges individual quarantine files itself.

The store performs all of those operations.

Commit behavior:

- revalidates containment/reparse safety immediately before publication;
- resolves duplicate names without overwrite;
- retries collision resolution if another store/process wins the chosen filename between resolution and `File.Move`;
- publishes only a size/digest-verified quarantine file;
- releases its reservation only after successful commit;
- deletes uncommitted partials on cancellation/failure;
- preserves already committed items if a later batch item fails;
- removes leftover per-session staging state on terminal exit.

## Compatibility

The public `WriteAndCommitAsync`, `GetQuarantinePath`, `CommitQuarantineFile`, `ResolveCollision`, staging/destination properties and three-argument constructor remain available for existing desktop/web callers.

`WriteAndCommitAsync` now delegates to the same reservation-backed streaming writer.

The Windows verification script was updated from a brittle literal `IncrementalHash` source check to require the new `StreamingSha256` and `ReserveIncoming` storage primitives.
