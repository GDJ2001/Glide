## Protocol correction: portable native channel binding

The pre-gate HARD-018 draft named `tls-exporter-v1`. That is not a portable implementation contract for the currently supported Android/.NET TLS stacks.

The native identity/resume transcript now uses:

`tls-server-spki-sha256-v1`

The 32-byte channel binding is the SHA-256 fingerprint of the TLS server certificate SubjectPublicKeyInfo actually used by the active pinned TLS connection.

The transcript also binds:

- the authenticated BOOTSTRAP/active session;
- fresh challenge message ID and 32-byte nonce;
- signer/verifier roles;
- both persistent identity fingerprints;
- the exact negotiated capability hash.

There is no zero-filled or connection-name fallback. A transport that cannot expose this authenticated binding cannot negotiate the trusted extension.

## Android LAN prerequisite correction

A concrete interoperability defect was found while binding identity proof to the authenticated session.

Before this work, Android LAN BOOTSTRAP created one random `sessionId`, but `TransferRuntime` created another random coordinator session after the connection event. A strict desktop receiver correctly requires HELLO to retain the BOOTSTRAP session id, so Android -> desktop could fail before any identity proof.

Added `AuthenticatedChannelContext` / `AuthenticatedChannelContextProvider` to the core transport boundary.

`LanTransferTransport` now records, per authenticated peer:

- the exact accepted/sent BOOTSTRAP session id;
- the TLS server SPKI SHA-256 binding.

`TransferRuntime` reuses that authenticated session id when constructing LAN sender/receiver coordinators. Nearby and transports without this authority do not implement the provider.

Prepared regressions assert:

- LAN sender and receiver expose the same BOOTSTRAP session;
- both expose the actual listener/server SPKI binding;
- the service-owned Android coordinator uses the authenticated BOOTSTRAP session rather than generating a second session.

Android LAN now advertises `identity-v1` dynamically **only** when the coordinator has both a persistent trust authority and an authenticated LAN channel context whose BOOTSTRAP session matches the transfer session. Nearby and transports without that authority continue to omit the capability. `resume-v1` remains disabled.

## Desktop mutual identity proof

Added `DesktopTrustedSessionAuthenticator`.

When both desktop peers negotiate `identity-v1`, identity authentication occurs after HELLO/HELLO_ACK and **before OFFER_BEGIN**.

Sender-side order:

1. send fresh identity challenge;
2. verify receiver response against session, roles, both identities, nonce, capability hash, and remote TLS server SPKI binding;
3. require enrolled expected identity when strict trusted-peer mode is configured;
4. receive the receiver's reciprocal challenge;
5. answer it using the sender persistent key.

Receiver-side order mirrors this:

1. receive and validate sender challenge;
2. answer using receiver persistent key;
3. send a fresh reciprocal challenge;
4. verify the sender response;
5. only then populate `DesktopOffer.AuthenticatedPeerFingerprintHex`.

The first challenge's claimed persistent fingerprint and the reciprocal response signer fingerprint must be identical. This prevents a peer from using one identity to initiate the exchange and another to answer it.

Known/revoked peer checks use `DesktopPersistentTrustManager`; key changes fail closed.

## Capability downgrade enforcement

Desktop HELLO offers `identity-v1` only when a persistent trust authority is present.

A HELLO_ACK may select `identity-v1` only if it was offered.

When an exact expected trusted fingerprint is configured, omitting `identity-v1` is an authentication failure before file offers.

`resume-v1` remains disabled.

## Explicit enrollment and headless authorization

`IDesktopTransferInteraction` now has an explicit verified-peer enrollment callback.

CLI interactive sessions:

- show the fully verified peer fingerprint;
- ask whether to trust the device;
- persist only after explicit yes.

Daemon mode:

- never enrolls;
- requires `--accept-paired-offers`;
- requires an already-enrolled `--trusted-peer <fingerprint>`;
- requires live identity-v1 proof of that exact fingerprint;
- then applies the existing peer-specific destination and byte ceiling.

The daemon offer policy therefore consumes a live authenticated fingerprint rather than stored trust alone.

CLI `send` and `receive` now also support optional strict `--trusted-peer <fingerprint>` mode. In strict mode a missing/revoked enrollment or capability downgrade fails closed.

WPF implements the new enrollment interface but deliberately returns not-approved; it does not yet pass a trust manager into transfer requests. This prevents silent trust enrollment while a dedicated fingerprint-confirmation UI is still outstanding.

## Android coordinator integration completed in source

The service-owned Android coordinator now owns the identity sub-handshake while leaving the existing transfer reducer responsible for HELLO/OFFER/item state.

When `identity-v1` is selected:

1. sender HELLO is sequence 1;
2. receiver HELLO_ACK is sequence 1;
3. sender challenge is sequence 2;
4. receiver response is sequence 2;
5. receiver reciprocal challenge is sequence 3;
6. sender reciprocal response is sequence 3;
7. only after both proofs succeed may sender emit OFFER_BEGIN at sequence 4.

The coordinator reserves identity control sequence numbers through the same mutex-backed outbound sequence state used by the reducer, so the identity extension does not create a parallel sequence space.

Offer metadata is rejected with `AUTHENTICATION_FAILED` if it arrives before required mutual proof. A 30-second identity deadline also fails closed.

Unknown but cryptographically verified peers are handed to `TransferRuntime.stageVerifiedPeerForEnrollment`; enrollment remains an explicit UI action. Already-enrolled peers are checked for exact key material and marked seen. Strict sessions may supply `expectedPeerFingerprintHex`; missing/revoked enrollment, fingerprint substitution, or omission of `identity-v1` then fails before any file offer.

Prepared JVM regression `TrustedSessionCoordinatorTest` proves the mutual-proof-before-offer ordering, continuous sequence numbers, authenticated peer fingerprints, verified enrollment handoff, and strict trusted-peer downgrade rejection.
