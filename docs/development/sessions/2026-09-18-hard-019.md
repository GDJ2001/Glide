# HARD-019 — Android persistent identity/trust integration preparation

## Status

**REVIEW_REQUIRED / pre-gate implementation** on `hardening/continue-2026-09-18`.

HARD-018 is REVIEW_REQUIRED and HARD-017 remains blocked on physical/native interoperability. This work prepares the Android persistent-trust runtime but does not enable `identity-v1` or `resume-v1` in production capability negotiation.

## Implemented

### Platform-neutral trust boundary

Added core ports:

- `PersistentIdentityStore`
- `TrustedPeerStore`

Added `PersistentTrustManager` for:

- local identity initialization;
- fail-closed restore handling;
- explicit verified-peer enrollment;
- duplicate enrollment refresh;
- last-seen updates;
- peer revocation;
- local identity rotation;
- trusted-peer lookup/snapshot.

### Verified enrollment authority

Added `IdentityProofVerifier`.

A peer can become enrollment-capable only after:

- `identity-v1` was negotiated;
- challenge message ID and nonce correlate;
- presented DER public key hashes to the advertised fingerprint;
- optional expected enrolled fingerprint matches;
- canonical HARD-018 transcript reconstructs from the active session;
- non-zero active channel binding is included;
- ECDSA transcript signature verifies.

The resulting `VerifiedPeerIdentity` constructor is not publicly forgeable by UI/discovery code.

### Android protected identity

`AndroidDeviceIdentityKeyStore` now implements `PersistentIdentityStore`.

- P-256 key pair generated in Android Keystore.
- Signing operates only on caller-supplied canonical transcript bytes.
- Local key presence is detectable.
- Explicit key deletion/rotation is supported.
- Private key remains inside Android Keystore.

The JVM adapter follows the same port for tests.

### Restored database without Keystore identity

If trusted-peer rows exist but the local identity alias is missing, `PersistentTrustManager.initialize()`:

1. creates a new local identity;
2. revokes all restored peer-trust rows;
3. reports `ResetAfterKeyLoss`;
4. requires re-enrollment.

Trust is never silently attached to a newly generated local key.

### Room trust adapter

Added `RoomTrustedPeerStore`.

Trusted peer domain records require canonical lowercase fingerprint/key hex and bounded display names.

`TrustedPeerDao` now supports `deleteAll()` for key-loss/rotation invalidation.

### Hilt/runtime integration

`DatabaseModule` provides singleton:

- `PersistentIdentityStore`;
- `TrustedPeerStore`;
- `PersistentTrustManager`.

`TransferRuntime` now exposes immutable `TrustRuntimeState` and owns:

- trust initialization/observation;
- pending verified enrollment;
- explicit approve/reject commands;
- peer revocation;
- local identity rotation;
- service-independent trust refresh/revoke/rotation for Settings.

Network/coordinator execution remains service-owned. Trust database management can run in a Settings/ViewModel coroutine without starting a foreground transfer service.

### Explicit enrollment presentation

`TransferScreen` displays a trust dialog only when runtime state contains a cryptographically verified pending identity.

The dialog:

- shows the peer display name;
- shows a shortened SHA-256 identity fingerprint;
- requires explicit **Trust device** or **Not now** action;
- states that remembered trust does not automatically accept future file offers.

No protocol path currently stages this dialog in production because HARD-021 has not yet wired live channel-bound identity exchange.

### Trusted-device presentation/revocation

Settings now presents core `TrustedPeerRecord` values.

In production:

- Settings mirrors `TransferRuntime.trustState`;
- revocation goes through the same `PersistentTrustManager` authority;
- the legacy direct-DAO path remains only as a compatibility/test fallback.

Stale UI language claiming mutual PIN enrollment or automatic resume was removed.

## Tests prepared

Core:

- restored trust database + missing local key revokes all trust;
- existing local key preserves trust;
- explicit approval enrollment;
- declined enrollment does not persist;
- duplicate enrollment refreshes rather than duplicates;
- local identity rotation revokes trust and changes fingerprint;
- channel-bound proof succeeds;
- proof replayed with another channel binding fails.

Android/app:

- trust management works without transfer-service scope;
- staged verified identity is not persisted before approval;
- wrong approval fingerprint fails;
- explicit approval persists;
- rejection never persists;
- Settings production path loads/revokes via runtime authority;
- hardened UI/source compliance checks explicit enrollment and no legacy PIN claims.

Shared HARD-018 tests now also reject all-zero synthetic channel bindings in Kotlin and .NET.
