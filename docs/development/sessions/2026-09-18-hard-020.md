# HARD-020 — Windows/Linux persistent identity/trust preparation

## Status

**REVIEW_REQUIRED / pre-gate implementation** on `hardening/continue-2026-09-18`.

HARD-018 and HARD-019 are still REVIEW_REQUIRED and HARD-017 remains blocked on physical/native interoperability. This work prepares the Windows/Linux persistent-trust boundary and peer-specific headless policy, but it does not enable production `identity-v1` trusted sessions. Live peer authentication remains owned by HARD-021.

## Implemented

### Protected persistent desktop identity

Added:

- `windows/Glide.Core/Security/DesktopTrustPaths.cs`
- `windows/Glide.Core/Security/DesktopPersistentIdentityStore.cs`

Windows uses a named current-user CNG P-256 signing key with private-key export disabled.

Linux stores a PKCS#8 P-256 key only under the user's Glide configuration directory, requires owner-only key permissions, rejects an existing key symlink, zeroes temporary encoded private-key buffers, and writes through an owner-only temporary file before atomic placement.

The desktop identity API exposes only:

- identity presence;
- public DER export;
- SHA-256 fingerprint;
- canonical transcript signing;
- explicit identity deletion/rotation.

No manual private-key export API is exposed.

### Versioned trust and headless-policy store

Added `DesktopTrustStore` with:

- schema version 1;
- canonical peer fingerprint/public-key validation;
- bounded display names;
- one peer record per fingerprint;
- one headless policy per enrolled peer;
- absolute destination roots;
- protocol-bounded maximum offer sizes;
- atomic temp-file replacement;
- Linux owner-only trust-file permissions;
- symlink rejection for the trust database path;
- fail-closed unknown-version handling.

The loader now also requires the explicit versioned field set. A versionless/legacy-looking JSON document cannot inherit the C# model's default version and be silently accepted as schema v1.

There was no prior supported desktop persistent-trust schema to migrate. Therefore HARD-020 deliberately uses fail-closed migration behavior rather than importing unauthenticated legacy/manual trust material.

### Verified enrollment authority

Added `DesktopPersistentTrustManager` and `DesktopIdentityProofVerifier`.

A peer can become enrollment-capable only after a HARD-018 identity proof verifies:

- `identity-v1` was negotiated;
- challenge message ID and nonce correlate;
- DER public key hashes to the advertised fingerprint;
- any expected enrolled fingerprint matches;
- the canonical identity transcript binds session, roles, both fingerprints, fresh challenge, negotiated capability hash, and the active secure-channel binding;
- the ECDSA signature verifies.

The resulting `VerifiedDesktopPeerIdentity` cannot be directly constructed by UI/CLI code outside the assembly.

Explicit enrollment, duplicate refresh, revocation, local identity rotation, and restored-trust/key-loss invalidation are centralized in the manager.

### Restore/key-loss behavior

At initialization, if the trust database contains peers/policies but the protected local key is absent, or the stored local fingerprint no longer matches the protected key:

1. a local identity is re-established;
2. all peer trust is revoked;
3. all headless policies are removed;
4. the caller is told that identity loss/change caused the reset.

Trust is never silently attached to a replacement local key.

### Peer-specific headless receive policy

The Linux/desktop daemon now requires both:

- explicit `--accept-paired-offers`; and
- `--trusted-peer <fingerprint>` matching an already-enrolled peer.

A policy binds that peer fingerprint to an exact destination root and maximum offer byte count.

`DesktopOffer.AuthenticatedPeerFingerprintHex` was added as the runtime authority input, but `DesktopTransferEngine` deliberately passes **null** today because HARD-021 has not yet performed live channel-bound identity proof. Consequently daemon offer acceptance remains fail-closed even when a stored peer policy exists.

This is intentional: stored trust alone must never be mistaken for proof that the current TCP/TLS session is that peer.

### CLI trust management

The desktop CLI now supports:

- `glide identity show`;
- `glide identity rotate --yes`;
- `glide trust list`;
- `glide trust revoke <fingerprint>`.

Manual fingerprint enrollment is intentionally not supported. Enrollment requires a cryptographically verified peer proof and will be connected to live sessions by HARD-021.
