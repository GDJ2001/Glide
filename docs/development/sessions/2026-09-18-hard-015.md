## Explicit incoming-offer authorization

### WPF

The previous WPF behavior returned `Task.FromResult(true)` for every authenticated offer.

`MainViewModel.ConfirmOfferAsync` now:

- projects the authenticated peer name, item list, relative paths, item sizes and total size;
- opens a dedicated incoming-offer modal;
- remains pending until the user selects **Accept & Receive** or **Reject**;
- observes the protocol cancellation token;
- closes/clears the modal in a `finally` path.

Because the shared engine requests consent before reservations/ITEM_READY, payload bytes are not authorized by the WPF path until the user explicitly accepts.

### Interactive CLI / daemon boundary

Interactive CLI receive now asks `Accept this transfer? [y/N]` and only accepts explicit `y`/`yes`.

Daemon mode does not inherit that interactive approval. It rejects the offer because HARD-016 still owns the explicit peer/destination/size policy required for unattended receiving.

## Persistent desktop state

A new shared `JsonDesktopStateStore` in `Glide.Desktop` persists local account-free desktop state.

Persisted settings:

- device display name;
- receive directory;
- verified-history retention limit (1–1000).

Persistence behavior:

- settings are validated before publication;
- receive directory must be an absolute path;
- writes are serialized;
- JSON is written to a same-directory temporary file, flushed, then replaced;
- in-memory state updates only after publication succeeds;
- malformed/unreadable state is preserved with a `.corrupt-<timestamp>` suffix when possible and safe defaults are used;
- history is ordered newest-first and pruned to the configured retention ceiling.

WPF loads the state at startup before transfer/listener actions consume settings.

The configured device name is used for QR invitation identity, DNS-SD advertisement, native send/receive HELLO identity and browser-share presentation. The configured receive directory is used by the real native quarantine store and the quick-open action.

## Durable verified history

`IDesktopTransferInteraction.OnHistory` was replaced by awaitable `OnHistoryAsync`.

The shared engine awaits the callback after each item is verified. This means a presentation/persistence implementation can durably record item history before that item progression completes.

WPF `OnHistoryAsync`:

1. appends the verified entry to `IDesktopStateStore`;
2. marshals collection projection onto the UI dispatcher;
3. applies the configured retention ceiling;
4. surfaces a truthful warning if persistence fails without retroactively declaring the already-verified payload invalid.

A partial batch therefore preserves history for already verified items while failed/unverified later items receive no verified-history row.

History can be cleared independently from received files and that clear operation is persisted.

## UI-thread-safe state boundary

WPF no longer reaches directly into `Application.Current.Dispatcher` from `MainViewModel`.

`IUiDispatcher` / `WpfUiDispatcher` owns thread affinity. Discovery events, protocol callbacks, persisted-state initialization and history collection mutations route through this boundary.

The view model has an internal dependency-injected constructor used by Windows UI tests so consent and background callback behavior can be exercised without starting mDNS or requiring production global state.

## User-facing WPF changes

`MainWindow.xaml` now includes:

- a fourth top-level **Settings** tab;
- device-name setting;
- receive-directory setting;
- history-retention setting;
- save-settings action;
- clear-history actions in Settings and History;
- a dedicated incoming-offer modal with peer, summary, file list and explicit Reject / Accept & Receive controls;
- a quick action labelled **Received Files** rather than hard-coded Downloads.

## CLI/WPF outcome parity

Both entrypoints still delegate transfer results to `DesktopTransferEngine`.

- WPF surfaces `DesktopTransferResult.Message` as `StatusMessage`.
- CLI now prints `[RESULT] <DesktopTransferResult.Message>` before returning its success/failure exit code.

An architecture regression test guards those two terminal projections.
